# AYN Thor performance verification — 2026-09-06

## Build and method

- Physical AYN Thor, existing 975-game library, landscape 1920×1080 main display.
- Built from worktree base `6cdc25f` plus the uncommitted cover-cache, cancellation,
  background-projection changes and device counters. Release, arm64, full AOT enabled.
- APK SHA-256: `475bfdcb0478701919daadaab42c88257e69348692c52f41ab9f688153b057ad`.
- Installed with `adb install -r`; signing certificate matched the installed local dev build.
  No uninstall, library reset, game-file edits or emulator launches were used.
- Switched from Shelf to Grid, CRT off. Enabled the existing FPS/render overlay and log sampler.
- Sent 120 downward controller inputs, then another 80; searched Mario and Zelda; cleared
  search and sent 15 next-platform and 15 previous-platform inputs, with 150 ms pauses
  between platform commands. Scrolling commands had 120 ms pauses plus ADB input overhead.
- Collected app-specific logcat counters, Android process memory, and screenshots. Disabled
  diagnostic overlays afterwards and left the dev build installed in the All Games grid.
- This is a verification of the new mechanisms, not a controlled before/after benchmark.
  No matched baseline frame-time trace or percentile measurement was collected.

### Memory

Android values below are KiB, collected with `dumpsys meminfo com.emushelf.app`.

| Phase | Total PSS | Total RSS |
|---|---:|---:|
| After first 120 scrolling inputs | 670,495 | 803,144 |
| After another 80 scrolling inputs | 668,727 | 801,372 |
| After searches and platform cycling | 721,647 | 854,912 |

Decoded-cover retention plateaued; total app memory is not capped at 64 MiB. Scope view models,
3D resources, native allocations, runtime/AOT code and other caches remain outside that budget.
The relatively stable PSS between the two scrolling passes supports the plateau, but later platform
visits still grew other app memory. Allocator residency can also outlast bitmap disposal.

## Remaining work / limits

- UI publication remains above a 16.7 ms frame budget; the 123.7 ms spike is a real remaining
  hitch. Measure its sub-phases, tile rebinding, second-screen observers and GC before choosing
  the next optimization. Do not label finding 3 fully fixed or claim smooth 60 FPS.
- The on-screen render graph recorded a 98.55 ms maximum during the browsing session, with
  diagnostics enabled. This is a screenshot observation, not a frame-time percentile benchmark.
- No AndroidRuntime crash output was returned for the test PID at the final check. This does
  not constitute an exhaustive ANR, lifecycle, battery, or multi-hour stability test.
- Resize coalescing is covered by automated tests; this device pass did not systematically resize
  the library viewport. Keyboard overlays were used for search.
- The Android build succeeded with existing nullability/platform API warnings in the Android head.
  After restoring the desktop dependency graph, all 11 selected cache/projection regression tests passed.

## First-launch follow-up

The user reported about 30 seconds of poor responsiveness only after replacing the previous
build. The original browsing pass did not measure this interval. Subsequent process-cold
launches reported Android activity launch times of roughly 1.3–1.4 seconds; Grid navigation
responded immediately afterward. Activity launch time does not measure full UI readiness.
The user subsequently confirmed the app remained responsive and could not reproduce the issue.
Its cause remains unconfirmed; this change does not claim to fix first-launch-after-update stalls.
